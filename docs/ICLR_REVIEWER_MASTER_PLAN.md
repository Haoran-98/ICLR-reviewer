# ICLR Reviewer 数字孪生审稿系统总体计划

> 历史路线图（2026-09-29）。文内阶段状态、Gate 与默认模型策略记录当时设计；后续已按用户指示完成领域库、按稿组合和独立 Web 审稿。当前事实与待完成项见 [STATUS.md](STATUS.md)，部署见 [DEPLOYMENT.md](DEPLOYMENT.md)。此处保留原始设计以供溯源，不作为当前进度或重新申请授权的依据。

## 1. 文档作用

本文档是项目的唯一总体路线图，用于控制进度、成本、数据边界和阶段验收。项目不一次性执行全部计划；每个阶段只有在产物通过验收且用户明确同意后，才能进入下一阶段。

本文档固定以下原则：

- ICLR 2024、2025、2026 每年都按固定比例划分训练、校准和测试子集，默认比例为 70%/15%/15%。
- 只研究 ICLR 主会，不导入或分析 Workshop。
- 所有会议稿件统一采用 ICLR 评分视角。
- 先建设离线数字孪生，再建设在线 Review/Rebuttal 服务。
- 普通 Python 和 SQL 能完成的任务不得调用 LLM。
- 默认使用弱模型，只有低置信度、冲突或无法判定的样本才能调用强模型。
- 不对全部论文预先深度理解所有公式、表格和图片。
- 所有推断必须保留来源、版本、置信度和不确定性，不将相关性伪装成因果结论。
- 自动化任务默认关闭；未经用户明确批准，不新增定时任务、开机启动或后台批处理。

## 2. 最终目标

系统最终形成两个协作但职责不同的数字孪生 Agent 组。

### 2.1 审稿人孪生组

根据用户上传论文的显式领域、隐式细分领域、方法类型和证据结构，自动选择最匹配的审稿人组合，完成：

- ICLR 风格评分与置信度估计。
- 新颖性、技术正确性、实验充分性、写作、伦理和可复现性审查。
- 领域专家与通用审稿人的独立评审。
- 对关键缺点给出论文内证据、影响和修复优先级。
- 对公式、表格和图片仅在问题触发时进行局部深度检查。
- 由 AC/Meta-Reviewer 汇总分歧，但不能通过简单平均掩盖致命问题。

### 2.2 投稿人孪生组

从作者角度协助：

- 识别论文最强贡献、最弱证据和可能被误解的叙事。
- 提供题目、摘要、Introduction、方法叙事和实验设计建议。
- 针对 Review 建立 concern ledger，并生成证据约束的 Rebuttal。
- 区分已解决、部分解决、未解决和无法验证的审稿问题。
- 预测哪些回复可能改变评分，哪些问题即使回复也难以改变决定。
- 与审稿人组进行多轮对抗，直到关键问题稳定或达到预算上限。

### 2.3 趋势与时间建模

系统必须显式建模年度变化，并在每个年度内部保留独立评测：

- 2024：70% 训练、15% 校准、15% 测试。
- 2025：70% 训练、15% 校准、15% 测试。
- 2026：70% 训练、15% 校准、15% 测试。
- 训练子集用于学习论文、Review、Rebuttal、评分和录用关系。
- 校准子集用于调整阈值、置信度、提示词和年度行为偏移；所有修改完成后冻结。
- 测试子集只用于该年度最终评测，不参与模型、标签、阈值、提示词或聚类边界选择。
- 2027：基于三年训练/校准结果和年度变化产生多角度趋势预测，并给出置信区间、支持证据和反例；不得输出确定性“必然趋势”。

除年度内 70%/15%/15% 划分外，系统保留独立的滚动时间评测：使用较早年份训练/校准，预测下一年份的测试子集，用于测量研究热点和审稿标准的跨年漂移。

## 3. 系统边界

### 3.1 本项目包含

- ICLR 2024–2026 主会论文、元数据、Review、评分、Rebuttal、Reviewer Response、Decision 和公开 revision/edit。
- 论文显式领域、多级隐式领域和跨领域关系。
- 论文结构化理解、领域检索、审稿人/投稿人原型和年度行为变化。
- Review、Rebuttal、多轮对抗、置信度和反事实分析。
- 证据可追溯的离线评测和在线服务。

### 3.2 本项目不包含

- Workshop 数据。
- 推断匿名审稿人的真实身份。
- 跨论文关联短 Reviewer ID。
- 用作者、机构或声誉直接影响论文评分。
- 预先对所有 PDF 运行完整视觉解析、OCR、公式恢复或表格重建。
- 把 Reviewer 沉默解释为同意。
- 把 Rebuttal 后接受直接解释为 Rebuttal 导致接受。
- 在任一年度的测试子集上调整模型、标签、阈值、提示词或领域边界。
- 在公开仓库暴露用户定制领域 Agent、私人稿件、认证信息或 API 原始请求。

## 4. 整体架构

```text
ICLR/OpenReview/本地全文
          |
          v
  [S1 数据与轻量全文层]
  raw -> core -> text-first index
          |
          v
  [S2 论文结构化理解]
  问题/Gap/Idea/方法/Claim/Evidence/限制
          |
          v
  [S3 多级领域体系]
  显式标签 -> 一级/二级/三级隐式领域 -> 跨领域边
          |
          v
  [S4 历史行为与因果证据]
  Review revision -> Rebuttal -> Reviewer response -> 分数变化
          |
          v
  [S5 数字孪生群体]
  Reviewer twins + Author twins + 年度条件
          |
          v
  [S6 离线评测与冻结]
  每年 70% train -> 15% calibrate -> 15% held-out test
  + 跨年度 rolling temporal evaluation
          |
          v
  [S7 在线 Review/Rebuttal]
  上传 -> 领域路由 -> Agent 组合 -> 按需证据解析 -> 输出
```

## 5. 数据与存储架构

### 5.0 年度分层数据划分

数据划分版本固定为 `annual_stratified_v1`。每年分别按以下比例划分：

| 年份 | 训练 | 校准 | 测试 | 年度论文数 |
|---|---:|---:|---:|---:|
| 2024 | 70% | 15% | 15% | 7,404 |
| 2025 | 70% | 15% | 15% | 11,672 |
| 2026 | 70% | 15% | 15% | 19,814 |

实现要求：

- 使用 `year + forum_id + split_version` 的稳定哈希分配，重复运行不得改变集合。
- 在每年内部按录用状态、显式领域和主要论文类型进行分层，避免某个子集只包含少数领域或单一录用状态。
- 同一论文及其所有版本、Review、Rebuttal 和 discussion 必须属于同一 split。
- 测试子集的标签、Review 和结果在训练与校准阶段不可见。
- 调整比例或分层字段必须创建新的 split version，不能覆盖旧划分。
- PostgreSQL 保存 split manifest、生成规则、随机种子/哈希盐、各层计数和对象哈希。

按总体数量估算，默认比例约为 27,223 篇训练、5,833 篇校准、5,834 篇测试；最终数量以分层后的冻结 manifest 为准。

S4 v4 的当前 200 篇已消费过旧 test，全部标记为开发数据，按 paper group 做开发交叉验证；
正式 held-out 评价另封存未消费论文。规则以 [完整计划](technical_details/S4_plan.md) 为准，
不覆盖其他阶段的 split manifest。

### 5.1 PostgreSQL

数据库固定为 `iclr_reviewer`，继续使用五个 schema：

| Schema | 职责 | 允许写入的内容 |
|---|---|---|
| `raw` | 不可变来源层 | 原始记录、OpenReview Note/Edit、artifact 清单、排除记录 |
| `core` | 规范实体层 | paper、version、review、revision、score、discussion、decision、area |
| `semantic` | 派生语义层 | 全文轻量索引、结构化理解、隐式领域、embedding、相关论文 |
| `twin` | 孪生模型层 | 专业原型、行为原型、Reviewer/Author twin、Rebuttal outcome |
| `ops` | 运行与审计层 | pipeline run、质量问题、snapshot、schema version、能力报告 |

向量继续使用 PostgreSQL + pgvector。当前不引入 Neo4j、MongoDB、Elasticsearch 或独立向量数据库。

### 5.2 对象存储

PDF、Markdown 和原始 JSON 继续按 SHA-256 存放在本地对象目录。数据库只保存哈希、路径、大小、类型、来源与质量状态。原始 `/data_big/iclr_reviews` 不修改、不删除。

### 5.3 在线缓存

Redis 只在在线阶段建设，用于用户临时上传、解析状态、短期检索缓存和 TTL 清理。离线阶段不提前引入 Redis。

## 6. 全文处理新策略

### 6.1 L0：来源保存

对所有论文保留：

- PDF/Markdown 是否存在。
- 文件哈希、路径、大小和来源。
- 标题、摘要、关键词和官方领域。
- 缺失状态，不使用空字符串冒充缺失内容。

### 6.2 L1：全量轻量索引

对所有已有 Markdown 使用 Python 正则和文本统计，提取：

- 正文字符数、token 数、估计页数和章节标题。
- Figure、Table、Equation、Theorem、Algorithm 的编号、caption、页码和字符位置。
- 理论敏感、结果表敏感、消融敏感、方法图敏感和正文疑似不完整等路由信号。
- `deep_parse_status=not_requested`，不自动运行深度解析。

离线历史论文默认使用已有 Markdown，不为全部论文重新运行 Docling 或 MinerU。

### 6.3 L2：Review 触发的局部解析

只有出现以下条件时，才解析对应页或对象：

- Reviewer 明确质疑某个公式、定理或证明。
- 论文声称 SOTA、显著提升或公平比较，需要检查主结果表。
- Reviewer 质疑组件有效性，需要检查消融表。
- 方法高度依赖架构图，正文不足以重建方法流程。
- 正文数字与表格、caption 或 Review 指向的数字不一致。
- 初步审稿对关键结论的置信度低于阈值。
- 用户明确要求检查某页、某图、某表或某公式。

局部处理顺序：

```text
已有 Markdown 上下文
    -> 对象页码/位置定位
    -> PDF 单页渲染
    -> MinerU/Docling/视觉模型局部解析
    -> Existing 文本层交叉核验
    -> 保存结果、来源与置信度
```

### 6.4 禁止的全量操作

- 不向 LLM 发送 MinerU Markdown 中的 base64 图片。
- 不为全部论文恢复全部 LaTeX 公式。
- 不为全部论文重建全部表格单元格。
- 不为全部论文理解每张图片。
- 不因检测到“存在公式/表格”就自动触发深度解析。

## 7. 论文结构化理解契约

每篇论文的结构化结果至少包含：

```json
{
  "problem": {},
  "motivation": {},
  "prior_gap": {},
  "core_insight": {},
  "method": {},
  "claims": [],
  "evidence": [],
  "datasets": [],
  "baselines": [],
  "metrics": [],
  "limitations": [],
  "explicit_areas": [],
  "implicit_taxonomy_candidates": [],
  "important_content_objects": [],
  "provenance": {},
  "confidence": {}
}
```

要求：

- Claim 与 Evidence 分开存储并建立引用关系。
- 事实、作者声称、模型推断和反事实假设使用不同字段。
- 每个派生字段记录模型、提示词版本、输入哈希和时间。
- 无法判断时使用 `unknown`，不能强行填充。
- 论文理解模型必须先经过固定样本评测，不能直接全量运行。

## 8. 多级领域体系

### 8.1 显式领域

- 合并 ICLR 2024–2026 官方领域标签的无重复集合。
- 保留原始标签、年份和标准化 alias。
- 一篇论文可属于多个显式领域。
- 用户在线上传时主动选择一个或多个显式领域。

### 8.2 隐式领域

在显式领域内部构建三级隐式分类：

- Level 1：稳定大领域，例如 Representation Learning、RL、Theory、Foundation Models。
- Level 2：方法或任务族，例如 Agent Learning、Educational AI、Causal Representation。
- Level 3：细分研究问题、技术路线或证据形态。

主方案：科学论文 embedding + 层级聚类 + LLM 命名与合并审核。

候选方法必须先做小样本对比，优先评测 SPECTER2、SciNCL 等科学文本表示；聚类候选包括层级聚类、HDBSCAN 和受约束聚类。最终方法在评测后固定，不在计划阶段宣称 SOTA。

### 8.3 跨领域关系

跨领域论文保留多个 assignment 和置信度，不强制唯一类别。图谱继续使用 PostgreSQL 节点表和边表；只有多跳查询出现明确性能瓶颈后才评估 Neo4j。

## 9. Reviewer Twin 建设

### 9.1 专业画像

Reviewer Twin 的专业画像来自：

- 审阅论文的显式与隐式领域。
- Reviewer Review 中关注的方法、任务、证据和缺陷类型。
- 评分置信度、严格程度和跨领域审查能力。
- 年度条件，避免把 2024 的标准直接复制到 2025/2026。

匿名 Reviewer alias 只在论文内有效，不跨论文识别真实个人。系统构建的是可审计的审稿行为原型，而不是现实人物复制品。

### 9.2 行为画像

至少包含：

- 新颖性敏感度。
- 技术正确性敏感度。
- 实验规模、基线、消融和统计要求。
- 理论证明要求。
- 写作与可读性要求。
- 伦理与可复现性要求。
- 评分分布、置信度和分数改变条件。
- Rebuttal 接受、部分接受和拒绝接受的证据模式。

### 9.3 在线组合规则

默认组合为：

- 2 个细分领域 Reviewer Twin。
- 1 个同一级大领域但不同细分领域 Reviewer Twin。
- 通用方法、实验、写作、伦理 Reviewer 继续参与，不被领域专家替代。
- 领域相关维度中，细分领域专家的初始证据权重可设为通用 Reviewer 的 1.5 倍；致命正确性问题不能被加权平均抵消。
- AC 根据证据质量、领域匹配和置信度综合，不按固定票数机械决定。

## 10. Author Twin 建设

Author Twin 不模拟真实作者身份，而模拟投稿策略原型：

- Idea 强、实验弱。
- 工程贡献强、理论弱。
- 理论贡献强、表达弱。
- Agent、教育、交叉领域等专业投稿原型。
- 善于 Rebuttal、证据补充、叙事重构或风险控制的行为原型。

Author Twin 输出必须受论文现有证据约束，不能捏造实验、引用、数据或结果。

## 11. Review/Rebuttal 因果分析

### 11.1 Rebuttal 成功信号

只有出现以下证据时，才能认为某个 concern 得到正向处理：

- Reviewer 明确表示 concern 已解决、部分解决或接受解释。
- Review revision 或后续回复体现态度改变。
- 分数或置信度变化与相应时间顺序一致。

“论文最终录用”不能单独作为 Rebuttal 成功证据。

### 11.2 未提分分析

系统同时分析：

- 回复未回答核心问题。
- 回答存在但缺少证据。
- Reviewer 接受解释但认为问题不影响原分数。
- 新问题抵消已解决问题。
- Reviewer 未回复，结果未知。
- 时间、评分冻结或流程因素导致无法更新。

### 11.3 反事实推论

每个反事实必须包含：

- 已观察事实。
- 因果假设。
- 可能混杂因素。
- 反事实条件。
- 支持与反对证据。
- 置信度。

系统不得把语言相似性或共现关系直接表述为因果结论。

## 12. 在线 Review 流程

1. 用户上传 PDF/Markdown/LaTeX，并选择显式领域。
2. 文件进入带 TTL 的临时缓存，不直接进入历史训练集。
3. 进行文本优先解析和结构化论文理解。
4. 结合用户显式领域与系统隐式领域确定领域分布。
5. 检索 2:1 的细分/邻近领域 Reviewer Twin，并加入通用 Reviewer。
6. 各 Reviewer 独立评分和记录证据，不先共享结论。
7. 如果某个 concern 指向图、表、公式或页面，触发局部深度解析。
8. AC 汇总 Review、置信度、证据和分歧。
9. 输出分项评分、总评、缺点、优先修改建议和反事实影响。
10. 到期清理临时文件和缓存。

## 13. 在线 Rebuttal 流程

1. 读取论文、Review 和可选的历史作者回复。
2. 将每条 Reviewer concern 拆为可验证的原子问题。
3. 判断 concern 是否需要正文、表格、公式、引用或新实验证据。
4. 仅对相关对象进行局部解析。
5. Author Twin 生成多个回答策略，但不得虚构证据。
6. Reviewer Twin 独立判断解决程度和可能分数变化。
7. 多轮对抗直到：关键问题稳定、达到轮数上限或缺少外部证据。
8. 输出最终 Rebuttal、逐条 concern ledger、残余风险和预计影响。

## 14. 模型与成本策略

### 14.1 模型分层

| 层级 | 用途 | 默认方案 | 升级条件 |
|---|---|---|---|
| Python/SQL | 清洗、统计、过滤、索引、关联、验证 | 标准库 + PostgreSQL | 不升级 |
| 开源模型 | embedding、聚类、可重复结构化任务 | 经小样本评测后固定 | 明显低于基线 |
| 弱 API 模型 | 论文结构化理解、标签命名、普通冲突 | `OPENAI_WEAK_MODEL_ID` | 低置信度或 unresolved |
| 强 API 模型 | 高价值冲突、因果判断、视觉裁决 | `OPENAI_STRONG_MODEL_ID` | 只由规则触发 |

### 14.2 成本控制

- 输入按章节或 claim 分块，不重复发送全文。
- 结果按输入哈希、模型和提示词版本缓存。
- base64 图片不得进入普通文本提示词。
- 视觉请求只发送被引用的单页或裁剪区域。
- 强模型调用必须记录触发原因和 token 使用量。
- 批量运行必须先完成 0.1%、1% 和固定验证样本门。
- 同一内容未变化时，重复运行变化数必须为零。

## 15. 主方案与备用方案

| 模块 | 主方案 | 备用方案 | 切换条件 |
|---|---|---|---|
| 历史全文 | 已有 Markdown 文本优先 | PDF `pdftotext` | Markdown 缺失或损坏 |
| 在线初始解析 | 轻量文本解析，必要时 Docling 单篇处理 | `pdftotext` + 章节规则 | Docling 不可用或延迟过高 |
| 表格/公式/图片 | 按页 MinerU/视觉模型 | Existing 文本层 + 人工核验 | OCR 冲突或 API 不可用 |
| 论文表示 | 科学文本 embedding | 通用 embedding | 科学模型部署失败或评测更差 |
| 隐式聚类 | 层级/受约束聚类 | HDBSCAN/BERTopic 风格流程 | 稳定性或可解释性不达标 |
| 向量检索 | pgvector HNSW | SQL 标签 + 全文检索 | pgvector 不可用或索引异常 |
| 图关系 | PostgreSQL 节点/边表 | Neo4j | 千万级节点或多跳查询瓶颈被测量确认 |
| LLM 批处理 | 弱模型优先 | 确定性规则/暂停队列 | API 故障、预算超限 |
| 冲突裁决 | 强模型局部调用 | 人工抽检 | 强模型不可用或涉及关键科学判断 |
| 在线缓存 | Redis TTL | 本地临时目录 + 清理任务 | Redis 尚未部署 |
| Reviewer 匹配 | 显式领域 + 隐式领域 + embedding | 标签与关键词规则 | embedding 检索置信度不足 |

## 18. 下一步逐项执行方案

### Step 1：完成 S1 轻量全文索引

输入：38,890 篇 core.paper 和已有 Markdown。

动作：已完成 `fulltext-index`；后续来源未变化时自动跳过全部记录。

产物：每篇论文一个 `semantic.paper_fulltext_index`，以及 figure/table/equation/theorem/algorithm 的轻量对象索引。

验收：

- 总行数 38,890。
- `indexed=38,715`，`missing=175`。
- 所有 `deep_parse_status=not_requested`。
- 第二次运行 `updated=0` 或仅包含来源真实变化。
- 抽检不少于 300 篇章节、caption 和页码定位。

备用：发现误检时升级 index version 并重建派生表；原始 Markdown 不受影响。

### Step 2：确定论文理解方法

输入：固定 50 篇，覆盖 ICLR 2024–2026、领域、接收状态和不同正文长度。

动作：使用弱模型比较单次全文结构化抽取、章节化证据抽取和 DocETL 式计划抽取；使用强模型对匿名随机排序的三路结果进行逐篇盲评。公式、图片和表格只在样本确实依赖它们时局部提供。

产物：50 篇全部完成。单次全文与章节化抽取的六项等权综合分均为 4.5067/5；单次全文胜出 22 篇、章节化胜出 21 篇、DocETL 式胜出 7 篇。完整结果见 `benchmarks/paper_understanding/50_paper_report.md`。

验收：已通过。强模型只用于本次离线方法评测，不进入生产抽取链路。

固定生产策略：

```text
弱模型单次全文结构化抽取
    -> Python schema 与证据检查
    -> 证据充分：保存结果
    -> 证据不足：同一弱模型执行章节化证据抽取
    -> 再次检查
    -> 仍不足：标记 needs_review，不自动调用强模型
```

以下任一条件触发章节化升级：核心字段缺失、关键 claim 没有证据、证据无法定位到输入正文、字段间存在冲突，或下游审稿任务明确要求严格可追溯性。正文长度本身不作为升级条件。DocETL 式计划抽取不进入生产路径。

### Step 3：建立三级领域体系

输入：keywords、title、abstract、introduction、conclusion、related_work 六板块原文及独立 embedding。

动作：四个独立 LLM 按每层三候选自由生成三级标签，以 embedding 提出联系和修复候选，
使用显式交叉投票和 DS/Crowd Layer 学习可靠性。官方标签只监督独立分类头，不锚定自由树。
不做人工抽查；即时执行，按 auth 并发，初次请求后最多五次重试。

产物：versioned taxonomy、paper assignment、typed 跨领域边和带明确语义的分数；生产冻结依赖 S3。

验收：当前 200 篇只做开发评价，细类无 gold 时不宣称真实准确率；未来封存论文只做冻结后的 assignment 评价。

备用：证据不足的候选保留 unknown/pruned，保留原文和拒绝日志，不强制生成三级节点。

### Step 4：Review/Rebuttal 轨迹建模

输入：Review revision、评分、Author Response、Reviewer Response、Decision。

动作：建立 concern、response、resolution、score change 和 unknown 状态；同时建模提分与未提分。

产物：可重放的对话树、Rebuttal outcome 和反事实证据表。

验收：所有 outcome 可追溯到 Note/revision；无回复不标记成功或失败。

备用：revision 不公开时，只使用可观察快照并降低置信度。

### Step 5：生成 Twin 原型

输入：论文专业画像和 Review 行为轨迹。

动作：先生成领域/行为 archetype，再生成组合 twin；不创建现实人物身份映射。

产物：Reviewer Twin、Author Twin、证据与年度条件。

验收：每个画像至少有规定数量的独立证据，且在三个年度的校准子集上分别完成置信度与行为偏移校准。

备用：证据不足的细分领域退回上一级 archetype，不用单篇 Review 生成画像。

### Step 6：离线闭集评测

输入：冻结的 2024、2025、2026 年度内训练/校准结果，以及三个年度均未见过的测试子集。

动作：分别评测每年的领域匹配、评分校准、Review 相关性、缺点覆盖、Rebuttal outcome 和反事实合理性；另外执行 2024→2025、2024–2025→2026 的滚动时间评测。

产物：测试报告、失败案例和是否进入在线阶段的 Gate 决策。

验收：各年度测试子集无泄漏；报告年度内结果和跨年漂移；与简单标签检索和单 Agent 基线比较；人工盲评确认可操作性。

备用：若评分预测不可靠，在线系统只输出 Review 与不确定性，不输出接受概率。

### Step 7：在线 Review MVP

输入：用户论文和显式领域。

动作：临时解析、论文理解、领域匹配、2:1 Reviewer 组合、独立 Review、按需证据解析和 AC 汇总。

产物：ICLR 格式 Review、分数、置信度、原因和修改优先级。

验收：核心工作流可重复；单篇成本与延迟满足预算；敏感文件到期清理。

备用：领域匹配失败时使用通用 Reviewer 组，并显式降低置信度。

### Step 8：在线 Rebuttal MVP

输入：论文、Review、可选补充证据。

动作：Concern ledger、Author Twin 回答、Reviewer Twin 复核、多轮终止。

产物：逐条回复、残余风险、预计评分影响和不能解决的问题。

验收：不虚构结果；每条回复引用论文或用户提供证据；无法解决的问题明确保留。

备用：证据不足时输出补实验/补解释清单，不生成假回复。

### Step 9：趋势预测与持续更新

输入：按年份冻结的领域、Review 和录用模式。

动作：分析投稿趋势、审稿趋势、idea 时效性和年度漂移。

产物：2027 多领域、多置信度预测。

验收：使用 2024 的训练/校准子集预测 2025 测试子集，使用 2024–2025 的训练/校准子集预测 2026 测试子集；没有回测支持的趋势只能标记为假设。

备用：趋势信号弱时输出情景分析，不输出单一路径预测。

## 19. 项目控制规则

### 19.1 阶段控制

- 每次只推进一个当前阶段。
- 阶段结束必须更新本文档的当前状态和验收结果。
- 未通过 Gate 时只能修复当前阶段或启用备用方案。
- 不因已有代码存在就默认该模块已完成。

### 19.2 数据控制

- 主会筛选依据 `track == "main"`。
- 原始层不可被派生结果覆盖。
- 所有缺失、冲突和失败显式记录。
- 每个派生结果可追溯到 paper、artifact、Note、模型和运行批次。

### 19.3 模型控制

- 模型选择必须有固定样本对比。
- 强模型不得成为默认批处理模型。
- API 失败时停止或进入可恢复队列，不无限重试。
- 同一阶段不得同时更换数据、模型、提示词和评测指标，以免无法解释变化来源。

### 19.4 人工决策边界

以下决策始终由用户批准：

- 研究目标和系统边界变更。
- 进入下一阶段。
- 采用新的外部模型或付费服务。
- 修改年度内 70%/15%/15% 比例、分层字段或 split version。
- 发布公共 Agent、数据或评测结果。
- 将用户定制 Agent 放入私人仓库。

## 20. 回滚与灾难恢复

- 原始 `/data_big/iclr_reviews` 始终保持不变。
- 数据库 schema 使用 Alembic 迁移，新增结构必须可 downgrade。
- 派生语义表可由原始层重新生成。
- 每个主要阶段完成后创建数据库 snapshot 和行数/哈希报告。
- taxonomy、profile、twin 和 prompt 都必须版本化；新版本失败时回退旧版本，不覆盖。
- API 中断时保留 checkpoint，不重复收费处理已完成样本。
- 在线临时数据故障时优先删除，不进入训练数据。

## 21. 最终完成定义

项目只有同时满足以下条件才视为完成：

- 数据库覆盖、缺失、revision 和对话关系通过验收。
- 论文理解和领域体系在固定验证集上稳定且可追溯。
- Reviewer/Author Twin 不依赖真实匿名身份推断。
- 2024、2025、2026 各年度测试子集均保持隔离，并另外保留跨年滚动评测。
- Review 与 Rebuttal 输出均包含证据、置信度和残余风险。
- 关键公式/表格/图片能够按需定位和解析，但未进行无意义的全量计算。
- 在线流程具有明确预算、超时、重试、缓存和清理规则。
- 公共仓库与私人个性化 Agent 边界通过审计。
- 2027 趋势输出经过历史回测，并区分事实、推断和假设。

## 22. 当前 Gate 决策

S1 已完成，S2 方法评测也已完成。当前已固定“弱模型单次全文默认、证据不足时使用同一弱模型章节化升级”的生产策略，但尚未获准开始全量 profile 入库。

在全量 profile 入库获得明确批准前，禁止开始：

- 全量论文 LLM 理解与 `semantic.paper_profile` 写入。
- 全量 MinerU/Docling 重解析。
- 隐式领域聚类。
- Reviewer/Author Twin 全量生成。
- 任一年度测试子集参与训练、校准或方法选择。
- 在线服务或自动后台任务。

下一步 owner 是结构化 profile 入库：先实现确定性的 schema/证据检查与断点续跑，再按固定策略处理论文。领域表示、embedding、聚类和 taxonomy assignment 仍属于后续独立 Gate。
